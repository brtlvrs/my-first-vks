# Open items

These surfaced while building this repo out from the `vks-apps`/`vks-platform` patterns and need a decision or verification before they can be called final. See `docs/` for what's already documented.

1. **Per-OS guidance in `docs/02-ssh-keys.md`.** Both key generation and SSH-agent setup are now broken out per macOS/Linux/Windows (including the Windows `icacls` fix for "permissions are too open", checked against current published best-practice sources: key expiry via `ssh-add -t`, `ProxyJump` over agent forwarding, unused-key hygiene) — but still not verified against a specific real customer's actual OS fleet. Review against what the real target team uses before treating it as fully final.
2. **vSphere Pods (`apps/hello-vsphere-pod/`) use case.** VM Service now has a documented candidate use case and a "declarative ≠ secure" framing written up in `apps/README.md#when-to-reach-for-vm-service` — vSphere Pods' own "when would you actually reach for this over a regular VKS-cluster app" is still open. Revisit once there's a concrete candidate workload.
3. **`cluster:delete` interactive picker (`fzf`).** Falls back to requiring the cluster name as an argument when `fzf` isn't installed — referenced as a tracked item from [`docs/10-day2-operations.md`](docs/10-day2-operations.md#deleting-a-cluster) and [`docs/12-troubleshooting-cookbook.md`](docs/12-troubleshooting-cookbook.md#clusterdelete-has-no-interactive-picker). Decide whether `fzf` should move from optional (`mise run doctor` reports it as a `WARN`, not a `FAIL`) to a required dependency, or whether the current name-argument fallback is good enough to leave as-is.
4. **Vault-backed SSH key storage.** [`docs/05-secret-management.md`](docs/05-secret-management.md) flags storing a platform engineer's own SSH key centrally in Vault (generate-or-fetch on a new machine, instead of re-generating by hand) as a natural extension once Vault is in place — but there's no Vault worked example in this repo yet at all, so it's currently just a mention with nothing to point to. Revisit once/if a Vault worked example gets built.
5. **Velero backup worked example.** [`docs/11-backups-with-velero.md`](docs/11-backups-with-velero.md) sketches the `VeleroService` shape but stops short of a full applied example (S3-compatible target, plugin image references, confirming Data Protection is enabled on the target Supervisor) — turn it into a real worked example, mirroring `apps/hello-vks/` and `platform/example-namespace/`, once someone has actually built one out end-to-end.
6. **Promote to `v1.0.0`.** Currently `v0.3.0` — per SemVer, `0.y.z` means "still initial development, anything may change." Promote once items 1 and 2 above are resolved and this repo has actually been used to onboard a real customer team, not before.
