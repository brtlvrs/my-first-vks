# Open items

These surfaced while building this repo out from the `vks-apps`/`vks-platform` patterns and need a decision or verification before they can be called final. See `docs/` for what's already documented.

1. **Per-OS ssh-agent guidance in `docs/02-ssh-keys.md`.** Checked against current published best-practice sources (key expiry via `ssh-add -t`, `ProxyJump` over agent forwarding, unused-key hygiene — all now added) — but still not verified against a specific real customer's actual OS fleet. Review against what the real target team uses before treating it as fully final.
2. **VM Service (`apps/hello-vm/`) and vSphere Pods (`apps/hello-vsphere-pod/`) use cases.** Both are wired up as working worked examples, but *when* to reach for either over a regular `hello-vks`-style app hasn't been fully discussed. One concrete VM Service candidate identified so far: a third-party vendor whose own support model is built around Podman/docker-compose and SSH access, not Kubernetes — handing them a VM (rather than asking them to containerize for K8s) meets them where they already are. Open sub-question: is a declaratively-provisioned VM (cloud-init from a reviewable, versioned spec) actually *more secure* than a manually-built one, or just more *reproducible and auditable* — which is a real, related, but not identical property? (Leaning toward the latter — declarative provisioning makes a VM's security posture reviewable and consistent, it doesn't automatically make that posture good; the cloud-init config, network exposure, and credential handling still have to be designed correctly, same as anywhere else.) Write this up properly (`apps/hello-vm/README.md` or a docs chapter) once settled, rather than asserting it as fact.
